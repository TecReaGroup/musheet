# MuSheet 后端登录与管理界面 UI 设计文档

## 1. 文档目标

本文档用于重新设计 MuSheet 后端登录页与管理后台界面，作为 `admin_web` 后续 UI 实现与迭代的统一依据。

设计目标：

- 保持与 app 端一致的品牌语义、色彩逻辑与组件气质
- 登录页简约、美观、可信，避免传统后台的“工具感过重”
- 管理后台布局稳定、层级清晰，支持高频操作与长时间使用
- 在桌面 Web 场景下建立比手机端更强的结构感，但不脱离 MuSheet 主设计系统

适用范围：

- 登录 / 首个管理员注册
- 后台主框架（导航、页面头部、内容容器）
- Dashboard / Users / Teams / Settings 四个核心页面
- 管理后台通用组件与状态规范

## 2. 设计结论

### 2.1 总体风格

后台界面采用以下组合方向：

- 主基调：`Minimalism & Swiss Style`
- 安全与可用性基线：`Accessible & Ethical`
- 产品属性参考：`SaaS / Productivity Tool / Collaboration Tool`

这意味着后台 UI 不做暗色控制台风格，也不做厚重企业化控制台，而是延续 MuSheet app 端已经建立的明亮、轻边框、低阴影、强信息秩序的产品语言。

### 2.2 与 app 端保持一致的核心原则

- 主色仍然以 `blue600` 为核心交互色
- setlist / 协作语义继续使用 `emerald600`
- 页面底色维持浅灰蓝白体系，不改成纯白大平面
- 主要组件仍是白色卡片 + 浅边框 + 中圆角
- 字体沿用系统风格，保持 `.SF Pro Text` 为默认体验方向
- 图标统一使用 Lucide，不引入第二套图标语言

### 2.3 视觉气质

关键词：

- 清爽
- 专业
- 可信
- 有秩序
- 不冷硬
- 对音乐协作产品友好

避免：

- 深色运维面板感
- 过度玻璃拟态
- 过多渐变与霓虹高饱和色
- 密集边框造成“表格软件”观感
- 把所有后台页面做成单纯的数据表

## 3. 品牌对齐策略

### 3.1 色彩策略

后台不新增独立品牌色，全部从 app 设计系统延展。

基础色板：

| 语义 | Token | 用法 |
|------|-------|------|
| 主操作 | `AppColors.blue600` | 登录按钮、主 CTA、选中导航、链接 |
| 主色浅底 | `AppColors.blue50` / `blue100` | Hero、统计卡、标签、聚焦区 |
| 协作色 | `AppColors.emerald600` | Team、shared resources、成功反馈 |
| 页面背景 | `AppColors.gray50` + 轻蓝偏移 | 整体工作区底色 |
| 主文字 | `AppColors.gray900` | 标题、数字、关键字段 |
| 次文字 | `AppColors.gray600` | 描述、二级说明 |
| 弱文字 | `AppColors.gray500` / `gray400` | 元信息、时间、说明标签 |
| 风险色 | `AppColors.red600` / `red50` | 删除、禁用、错误 |

补充规则：

- Dashboard 中紫色仅作为辅助区分，不作为主品牌色
- Login 背景允许使用 `blue50 -> white -> emerald50` 的低饱和渐变
- 数据可视化颜色优先使用蓝、绿、灰；避免过多彩色柱状与饼图

### 3.2 字体策略

后台与 app 端统一使用系统无衬线体系，不额外引入展示型字体。

原因：

- MuSheet 现有主题已经建立系统字体体验
- 管理后台是高频操作工具，不适合强调装饰型标题
- 保持与 Flutter app、Flutter Web 的实际实现成本一致

排版层级：

| 层级 | 建议字号 | 字重 | 用法 |
|------|----------|------|------|
| 页面标题 | 28-32 | 700 | Login 标题、Dashboard 标题 |
| 模块标题 | 20-24 | 700 | 卡片区块、弹窗标题 |
| 卡片标题 | 16-18 | 600/700 | 表格卡、统计卡、设置组 |
| 正文 | 14 | 400/500 | 描述、说明、表单文案 |
| 标签 | 12-13 | 600 | Pill、Badge、栏目说明 |
| 元数据 | 11-12 | 400/500 | ID、时间、状态补充 |

### 3.3 形状与阴影

为保持与 app 一致，后台界面继续使用中圆角，但桌面端略大于移动端。

| 元素 | 圆角 |
|------|------|
| 主卡片 / Surface | 24 |
| 二级卡片 / Panel | 20 |
| 输入框 / 按钮 | 16 |
| Badge / Pill | 999 |
| 小型图标容器 | 12 |

阴影规则：

- 常规卡片：优先只用边框，不依赖阴影
- 重点浮层：允许 `0 8 30 rgba(15, 23, 42, 0.08~0.12)` 的柔和阴影
- 登录页表单与 Hero 区可有极轻投影，但不可出现厚重悬浮感

## 4. 后台登录页设计

### 4.1 页面目标

登录页不仅是鉴权入口，还要传达以下信息：

- 这是 MuSheet 的管理员工作台
- 视觉上属于同一个产品，不是独立外包后台
- 首次注册、常规登录都应清楚、可信、无噪音

### 4.2 布局结构

桌面端采用 `6:5` 双栏布局。

左侧：品牌与后台价值说明  
右侧：登录 / 注册表单

结构如下：

```text
┌──────────────────────────────────────────────────────────────┐
│ light gradient background                                   │
│  ┌──────────────────────────┐  ┌──────────────────────────┐  │
│  │ Brand / Intro Panel      │  │ Login Form Card          │  │
│  │ - Wordmark               │  │ - Welcome title          │  │
│  │ - Admin workspace label  │  │ - Username               │  │
│  │ - 3 feature highlights   │  │ - Password               │  │
│  │ - 3 metric pills         │  │ - Error / tips           │  │
│  │ - Trust message          │  │ - Primary CTA            │  │
│  └──────────────────────────┘  └──────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

响应式策略：

- `>= 860px`：双栏
- `< 860px`：上下堆叠
- `< 560px`：表单卡片保持单栏，减少说明性内容密度

### 4.3 视觉规则

背景：

- 不是纯色
- 使用极轻的冷暖混合渐变
- 不做大面积插画，不做音乐符号纹理

左侧介绍面板：

- 作为情绪与信息引导区
- 使用白色卡片表面 + 浅边框
- 顶部展示 `Admin Workspace` 标签
- 中间用 1 句主标题 + 1 段说明明确平台价值
- 底部列 3 个功能点，控制在两行内

右侧表单卡：

- 层级应更集中、更高对比
- 标题与说明靠近首屏交互，不要让输入框距离标题过远
- 首次注册提示使用 `blue50` / `yellow50` 轻提示条
- 错误提示使用内联消息，不要靠 snackbar 替代

### 4.4 登录页组件规则

输入项：

- 标签在输入框上方，左对齐
- 输入框高度建议 `52-56`
- 图标只作为辅助识别，不可压过输入内容
- 密码显隐按钮固定在 suffix，不位移布局

CTA：

- 主按钮固定为整行宽
- 文案简洁，登录用 `Sign in`，注册用 `Create account`
- Loading 时保留按钮宽度，不可跳动

辅助链接：

- 放在卡片底部
- 使用句子 + 文本按钮模式
- 不与主按钮争抢视觉权重

### 4.5 登录页信息层级

必须按以下顺序呈现：

1. 品牌识别
2. 页面目的
3. 当前操作模式（登录 / 注册）
4. 主要字段
5. 风险或限制说明
6. 主按钮
7. 模式切换

不建议加入：

- 复杂品牌故事
- 大段帮助文本
- 多个并列 CTA
- 过多安全术语

## 5. 管理后台总布局设计

### 5.1 整体框架

后台使用“左侧导航 + 右侧主工作区”的稳定壳层，不采用顶部菜单主导航。

原因：

- 管理页面是多页面频繁切换场景
- 左侧导航更利于稳定定位与未来扩展
- 与表格、卡片、表单共存时结构更清晰

整体结构：

```text
┌────────────────────────────────────────────────────────────────────┐
│ page background                                                   │
│ ┌──────────── Sidebar ────────────┐ ┌──────── Main Surface ─────┐ │
│ │ brand                           │ │ top page header           │ │
│ │ workspace summary               │ │ hero / quick actions      │ │
│ │ nav list                        │ │ page content cards        │ │
│ │ current admin profile           │ │ table / chart / forms     │ │
│ └─────────────────────────────────┘ └────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────┘
```

### 5.2 侧边栏规范

宽度：

- 宽屏：`288`
- 紧凑桌面：`240`
- 小屏桌面 / 平板横屏：可折叠为图标栏，但当前阶段先保持展开态

内容顺序：

1. Wordmark
2. 当前工作区简介卡
3. Navigation 标题
4. 导航列表
5. 当前管理员信息卡

导航项规则：

- 选中项使用 `blue600` 浅底或实底强调
- 图标大小统一 `18-20`
- 标签不要超过两个单词
- Hover 只改底色和文字色，不做位移动画

### 5.3 主工作区规范

主工作区不是满屏白底，而是一个“被背景包裹的内容容器”。

要求：

- 与侧边栏之间保留外边距
- 主工作区内部再建立统一页面边距
- 页面头部、Hero、正文区形成稳定节奏

建议尺寸：

- 外层边距：20
- 主容器圆角：24
- 页面内边距：24-28
- 区块垂直间距：24

### 5.4 页面头部模板

所有核心页面统一采用三段式头部：

1. `eyebrow`
2. `title + subtitle`
3. `actions`

规则：

- 标题与操作按钮在同一视觉区域
- 副标题只讲当前页目标，不重复系统介绍
- 操作按钮最多 2 个主入口，其余收敛到表格行内或弹窗

## 6. 核心页面设计

### 6.1 Dashboard

#### 页面目标

- 让管理员 5 秒内理解平台概况
- 把高频总览信息置于最上方
- 图表只承担辅助分析，不压过业务数字

#### 推荐结构

1. 页面头部
2. Hero 摘要区
3. KPI 四卡
4. 图表双栏
5. Team overview 表格

#### 布局规则

- KPI 区优先 4 列；窄屏自动变 2 列或 1 列
- 图表区仅保留 2 个最有解释力的图
- 团队表格保持完整宽度，不与图表混排在同一行尾部

#### 视觉重点

- 第一视觉焦点是 Hero 标题和 KPI 数字
- 第二视觉焦点是 Team activity 图表
- 表格是信息确认层，不应抢占 Hero 的视觉权重

### 6.2 Users

#### 页面目标

- 支持管理员快速扫描账号状态
- 把高风险动作清晰隔离
- 让“查看用户”和“操作用户”在同一流中完成

#### 推荐结构

1. 页面头部
2. Hero 摘要区
3. 筛选与快速操作条
4. 用户表格
5. 分页区

#### 表格字段优先级

高优先：

- User
- Role
- Status
- Created
- Actions

低优先：

- ID
- Display name

设计建议：

- `User` 列使用头像 + 用户名 + ID 的组合
- `Status` 与 `Role` 都使用 badge，不用纯文本
- 风险动作放在最后，且和普通动作之间留间距
- “当前会话”不可操作，直接显示只读状态

#### 建议新增的布局优化

- 在表格上方增加轻量过滤条
- 支持 `All / Admin / Disabled` 分段筛选
- 搜索框位于右上或左上，不与主按钮竞争

### 6.3 Teams

#### 页面目标

- 明确团队数量、成员规模、共享资源三类信息
- 把“查看成员”和“删除团队”区分开
- 支持团队创建与成员管理的连续操作

#### 推荐结构

1. 页面头部
2. Hero 摘要区
3. 团队目录表格
4. 分页区
5. 弹窗式成员管理流

#### 表格设计

- 团队名称列展示 `name + team id`
- 成员数与共享乐谱数都用 count badge
- 行操作只保留两个高频操作：`View members`、`Delete`

#### 成员管理弹窗

成员弹窗应采用“标题 + 操作按钮 + 内容表格”的稳定模板。

规则：

- 顶部右侧只有一个 `Add member`
- 内容区不足时显示空状态，不留大块空白
- 删除成员使用行内危险图标按钮 + 二次确认

### 6.4 Settings

#### 页面目标

- 提供低频但重要的系统配置
- 明确分组，避免像 Dashboard 一样拥挤
- 把账号信息、系统状态、后续能力拆开

#### 推荐结构

1. 页面头部
2. Account card
3. System health card
4. Platform controls card
5. About / metadata card

#### 设计要求

- 设置页面不使用大型图表
- 每组只放一种任务类型
- 风险设置单独成组并给出说明

## 7. 通用组件规范

### 7.1 Surface

后台所有可复用容器分三级：

- `Page Surface`：主工作区外层
- `Section Card`：模块容器
- `Inset Surface`：表格内说明块、提示块、子模块

规则：

- 同一页面内最多三层表面
- 不允许在白卡里再连续嵌套三层白卡
- 强调层用浅色背景，不用加重阴影

### 7.2 Hero 区

Hero 只出现在页面顶部，承担“这一页是什么”和“关键指标是什么”。

规则：

- 左侧：标题与说明
- 右侧：2-3 个 pill 指标
- 背景：轻蓝白或蓝绿白渐层
- 不放表单与复杂筛选

### 7.3 KPI Card

结构：

- 图标容器
- 指标标签
- 核心数字
- 补充说明或趋势

规则：

- 数字字号明显大于标题
- 每张卡只表达一个指标
- 不在同一张卡里放多个统计值

### 7.4 Data Table Card

规则：

- 表头区必须有标题、说明、图标
- 表体要允许横向滚动，但卡片本身占满父容器
- 表头背景用 `gray50`
- 行高稳定在 `64-72`
- 操作列永远放最后

### 7.5 Dialog

后台弹窗用于：

- Create user
- Create team
- Add member
- Confirm destructive action
- Temporary password reveal

规则：

- 默认宽度 `420-760`
- 标题、内容、操作区层次明确
- 长表格类弹窗应固定高度并允许内部滚动
- 危险确认弹窗文案必须简短、直接、明确后果

### 7.6 Badge / Pill

Badge 用于状态，Pill 用于统计摘要。

规则：

- Badge 颜色必须有明确语义
- Pill 更偏信息摘要，视觉比 Badge 更轻
- 不要把红色用在普通计数型 pill 上

## 8. 状态设计

每个页面都必须覆盖：

- loading
- empty
- error
- success feedback
- destructive confirm

### 8.1 Loading

- 页面首屏使用居中 loading
- 表格刷新使用按钮内 spinner 或局部 loading
- 不要整页反复闪烁重载

### 8.2 Empty

空状态包含三部分：

1. 图标
2. 一句话说明当前没有内容
3. 一个明确下一步动作

### 8.3 Error

错误信息分级：

- 页面级错误：居中空状态
- 区块级错误：卡片内提示条
- 操作失败：toast

### 8.4 风险操作

以下动作统一视为危险操作：

- Delete user
- Delete team
- Deactivate user
- Demote admin
- Remove member

规范：

- 行内按钮先触发确认弹窗
- 弹窗主按钮使用危险色
- 文案明确说明是否可恢复

## 9. 响应式与适配

### 9.1 断点建议

| 断点 | 场景 | 规则 |
|------|------|------|
| `>= 1280` | 宽屏桌面 | 完整侧边栏，KPI 4 列，图表双栏 |
| `1024 - 1279` | 标准桌面 | 侧边栏收窄，图表仍可双栏 |
| `768 - 1023` | 小桌面 / 平板横屏 | 内容密度降低，部分区域改单栏 |
| `< 768` | 平板竖屏 / 手机 Web | 尽量避免复杂后台使用，导航需折叠 |

### 9.2 响应式优先级

- 先保证读取和操作不出错
- 再保证表格可横向滚动
- 最后才处理“看起来不空”的视觉优化

后台不应简单把移动端 UI 拉宽，也不应把桌面表格硬塞进小屏。

## 10. 动效与交互

### 10.1 动效原则

- 动效只用于增强层级与反馈
- 时长控制在 `150-250ms`
- 不使用大位移、不使用弹跳式 hover

### 10.2 建议动效

- Hover：背景色 / 边框色平滑变化
- Dialog：轻淡入 + 轻上移
- Sidebar item：背景高亮过渡
- Button：颜色过渡，不缩放

### 10.3 不建议动效

- KPI 数字大幅跳动
- 数据表行 hover 位移
- 大面积渐变持续运动
- 登录页左右面板夸张进场

## 11. 可访问性要求

必须满足：

- 交互目标最小 `44x44`
- 表单字段有明确 label
- 焦点态清晰可见
- 颜色不是唯一状态判断依据
- 表格操作按钮有 tooltip
- 风险按钮文案明确

额外要求：

- 登录页主按钮与输入框对比度需满足 WCAG AA

## 14. 最终设计原则

MuSheet 后台不是“另一套后台模板”，而是 MuSheet 产品体验在桌面管理场景的延伸。

因此最终视觉判断标准不是“像不像常见 admin dashboard”，而是：

- 是否保留了 MuSheet app 的干净、可信、轻量气质
- 是否让管理员在高频任务里快速看清信息、快速做对操作
- 是否在桌面 Web 场景下建立了更稳定、更高级的布局秩序

只要持续围绕这三点推进，后台登录与管理界面就能在风格和实用性上同时成立。
